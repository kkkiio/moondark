五种 users 表存储方案

左侧为表结构与归属，右侧为注册 / 请求时的数据流。

A 同表部分投影：Auth 只读写核心列
Lucia v2 / Devise
表结构
TABLE users（单表共享） App 建表
id, display_name, is_active, created_atAuth 读写
role, avatar, bio（需允许 NULL 或有 DEFAULT）App 读写
请求数据流
  1. Middleware 查询核心列
    SELECT id, display_name, … → UserModel
  2. Handler 补查业务列
    SELECT role, avatar … WHERE id = ?
  • 单表，无需 JOIN
  • 含 NOT NULL 业务列时无法直接 register
  • 每次请求需查询 2 次
B 认证表与 Profile 表物理分离
Supabase / Keycloak
表结构
auth_users Auth 独占
idPK
is_activeBOOL
created_atBIGINT
1 : 1 FK user_id
user_profiles App 独占
user_idPK, FK
usernameVARCHAR
tenant_idBIGINT
数据流
  1. Auth.migrate() 管理 auth_users
    框架自行建表与迁移
  2. 注册时写入两张表
    INSERT auth_users → INSERT user_profiles
  3. 读取完整用户
    JOIN 或分两次查询
  • 框架表与业务表物理隔离
  • 注册需写两张表
  • 读取需 JOIN
C Trait 契约 + 应用提供 load_user
Rust axum-login
表结构
struct AppUser : AuthUser（TABLE users） App 独占
fn id(self) -> Int64 / fn is_active(self) -> BoolTrait 契约
id, username, tenant_id, role, is_active…任意业务列
请求数据流
  1. Session 读取用户 ID
    _auth_user_id = 42
  2. 调用 App 的 load_user(42)
    应用 SQL 一次查出 AppUser
  3. 存入 req.ctx
    Handler 直接取得 AppUser
  • 每次请求 1 次 SQL
  • Handler 拿到强类型 AppUser
  • 凭据存储需另行提供
D Auth 只管 credentials 表，users 表归应用
Lucia v3 / WebAuthn
表结构
TABLE users（应用定义与读写） App 独占
idBIGINT PK
username, tenant_id, role…任意 NOT NULL 列
is_activeBOOL
1 : N 逻辑关联 user_id
TABLE user_credentials Auth 独占
(kind, provider, identifier)UNIQUE KEY
user_idBIGINT INDEX
secret, verified, last_used_at凭据哈希 / Token
注册与登录数据流
  1. 注册：App 插入 users 表
    INSERT INTO users (…) → user_id
  2. 绑定凭据：Auth 写 credentials 表
    auth.set_password(user_id, …)
  3. 登录验证：Auth 查 credentials 表
    authenticate_password() → Some(user_id)
  4. 会话加载（与 C 组合时）
    load_user(user_id) → AppUser 注入 req.ctx
  • 框架无需 create_user / update_user
  • user_credentials 结构固定，可由框架提供 SQL Store
  • 注册支持任意必填业务列
  • 注册流程由 App 与 Auth 两步完成
  • 单独使用时 Handler 仅拿到 user_id，需与 C 组合加载用户
E 固定核心列 + JSON Metadata 列
Auth0 / PocketBase
表结构
TABLE users Auth 接管
id, display_name, is_active, created_at固定核心列
metadata: {"role": "admin", "tenant_id": 10}JSONB / TEXT
请求数据流
  1. Middleware 加载 UserModel
    metadata: Map[String, Json]
  2. 业务代码读取扩展字段
    手动解析 Json 并判空
  • 无需修改表结构，适合托管 SaaS
  • 每次请求 1 次 SQL
  • 扩展字段无静态类型检查
  • 无法对扩展字段建 SQL 外键约束
