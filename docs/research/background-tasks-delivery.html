Background Tasks 投递语义与 API 设计调研

对比 Django 6.0、Celery、Go River、Rust Underway、Elixir Oban 与 Scala Akka Typed 的 Task 类型与 enqueue 签名设计。

  • 端到端 At-Least-Once 由 入队、认领、重试、幂等 4 个环节共同决定，只要有一环缺失，投递保证就不成立。
  • SQL 队列（River / Underway / Oban）默认 At-Least-Once，但「必须在事务里入队」只能靠文档约定，因为裸 Insert 始终可以直接调用。
  • 只有 Akka Typed 用两套类型在编译期区分两种语义。

为什么裸 enqueue 做不到 At-Least-Once？

投递保证由 4 个物理位置串联决定，缺失任一环都会落到对应的失败模式。

环节At-Most-Once 写法At-Least-Once 写法
① 调用点先 Commit 后 enqueue 崩溃即丢
先 enqueue 后 Commit 竞态 / 幽灵任务		enqueue(backend, tx) 与业务同事务提交
② 认领Early Ack 取走即删Lease / Reclaim 超时回收
③ 异常max_attempts = 1 报错直接 Failedmax_attempts > 1 退避重回 Ready
④ 函数体—DB 写入用唯一键 / 状态机；外部 API 传 idempotency_key 用户责任

横向对比：默认语义 × 约束手段

SQL 队列普遍是「默认参数 + 文档约定」；Akka Typed 用「独立类型」在编译期强制区分。

代码对照：Task 是什么类型？怎么 enqueue？

各库定义一个任务并入队的最小写法。

Go · River MaxAttempts=25 + 文档推荐 InsertTx

Task 类型
struct SyncBillArgs（实现 JobArgs）
入队方法
client.InsertTx(tx, args) / client.Insert(args)
编译期限制
无，任何 Job 都能裸调 Insert
type SyncBillArgs struct { BillID int }
func (SyncBillArgs) Kind() string { return "sync_bill" }
func (SyncBillArgs) InsertOpts() river.InsertOpts {
    return river.InsertOpts{ MaxAttempts: 5 } // 不写默认 25
}

// 1. 事务入队（推荐）
_, err := client.InsertTx(ctx, tx, SyncBillArgs{BillID: 42}, nil)
// 2. 非事务入队（编译器不报错，存在丢任务窗口）
_, err  = client.Insert(ctx, SyncBillArgs{BillID: 42}, nil)

Rust · Underway RetryPolicy::default() + 双入队方法

Task 类型
Job<Input, State>
入队方法
job.enqueue_using(&mut *tx, &in) / job.enqueue(&in)
编译期限制
泛型只约束 Input，不约束是否进事务
let sync_bill: Job<SyncBill, ()> = Job::builder()
    .step(|_cx, SyncBill { id }| async move { To::done() })
    .name("sync_bill").pool(pool).build().await?;

// 1. 事务入队
sync_bill.enqueue_using(&mut *tx, &SyncBill { id: 42 }).await?;
// 2. 连接池直接入队（同样随时可调）
sync_bill.enqueue(&SyncBill { id: 42 }).await?;

Elixir · Oban max_attempts: 20 + Ecto.Multi

Task 类型
Oban.Changeset（由 Worker.new/2 构造）
入队方法
Oban.insert(multi, name, cs) / Oban.insert(cs)
编译期限制
无（动态类型）
defmodule MyApp.SyncBill do
  use Oban.Worker, max_attempts: 5, unique: [period: 60]
  def perform(%Oban.Job{args: %{"id" => id}}), do: :ok
end

# 1. 绑进 Ecto.Multi 事务
Ecto.Multi.new()
|> Ecto.Multi.insert(:bill, bill_cs)
|> Oban.insert(:job, MyApp.SyncBill.new(%{id: 42}))
|> Repo.transaction()

Scala · Akka Typed 两套类型，编译期强隔离

AtMostOnce 类型
ActorRef[Cmd] → 直接 ref ! msg
AtLeastOnce 类型
ProducerController[Cmd] + Delivery[Cmd]
编译期限制
AtLeastOnce 不能裸发，Consumer 强制带 confirmTo
// At-Most-Once：普通 ActorRef，直接 ! 发送
smsActor ! SendSms("13800000000")

// At-Least-Once：只能在收到 RequestNext 令牌时通过 sendNextTo 发送
case WrappedRequestNext(next) =>
  next.sendNextTo ! SyncBill(42)

// Consumer 端类型被强制包裹，必须显式发 Confirmed
case ConsumerController.Delivery(SyncBill(id), confirmTo) =>
  syncBill(id)
  confirmTo ! ConsumerController.Confirmed

Python · Django 6.0 django.tasks 只定义接口契约，不含重试参数与 Worker

Task 类型
django.tasks.Task
入队方法
task.enqueue(*args, **kwargs)
事务结合
靠 transaction.on_commit(...)（Commit 后崩溃仍会丢）
@task(priority=10, queue_name="default", takes_context=True)
def sync_bill(context: TaskContext, bill_id: int):
    # context.attempt 从 1 开始，但 @task 无 max_attempts 参数
    ...

with transaction.atomic():
    Bill.objects.create(id=42)
    # 注意：on_commit 在事务提交后执行，若此时进程崩溃，任务丢失
    transaction.on_commit(partial(sync_bill.enqueue, bill_id=42))

Python · Celery 装饰器上的三个参数切换语义

AtMostOnce（默认）
acks_late=False, max_retries=0
AtLeastOnce
acks_late=True, reject_on_worker_lost=True
入队方法
task.delay(...) / task.apply_async(...)
# 1. At-Most-Once（Worker 拿到消息先 ACK，崩溃绝不重跑）
@app.task(acks_late=False, max_retries=0)
def send_sms(phone: str): ...

# 2. At-Least-Once（执行完才 ACK，进程被杀自动重回队列）
@app.task(acks_late=True, reject_on_worker_lost=True, max_retries=5)
def sync_bill(bill_id: int): ...
