Auth 框架中 users 表存储方案调研

聚焦「框架核心列 vs 应用自定义列」的存储边界，梳理不同语言社区的演进路径与五种常见架构。

  • Auth 框架一旦接管 users 表，就会和业务列冲突：注册时 INSERT 缺必填列，请求时要再查一次业务列（N+1）。
  • 动态语言靠继承加反射把两类列合进一张表；Go / Rust / MoonBit 这类静态、无继承的语言做不到，社区的走向是 Auth 只管凭据（Lucia v3、WebAuthn）。
  • D + C 组合：框架管 user_credentials，应用管 users 并提供 load_user。MoonDark 的 CredentialStore + SessionAuth(load_user~) 就是这个方案。

当 Auth 框架直接接管 users 表时

框架定义的固定结构与业务真实的表结构在同一张表上相遇。

语言特性与社区演进

语言是否支持继承 / 运行时反射，决定了「扩展用户字段」的实现方式。

五种 users 表存储方案

每个方案左边是表结构与归属，右边是注册 / 请求时的数据流。

A · 同表部分投影：Auth 只读写核心列 Lucia v2 / Devise

  • 单表，无需 JOIN
  • 含 NOT NULL 业务列时无法直接 register
  • 每次请求需查询 2 次

B · 认证表与 Profile 表物理分离 Supabase / Keycloak

  • 框架表与业务表物理隔离
  • 注册需写两张表
  • 读取需 JOIN

C · Trait 契约 + 应用提供 load_user Rust axum-login

  • 每次请求 1 次 SQL
  • Handler 拿到强类型 AppUser
  • 凭据存储需另行提供

D · Auth 只管 credentials 表，users 表归应用 Lucia v3 / WebAuthn

  • 框架无需 create_user / update_user
  • user_credentials 结构固定，可由框架提供 SQL Store
  • 注册支持任意必填业务列
  • 注册流程由 App 与 Auth 两步完成
  • 单独使用时 Handler 仅拿到 user_id，需与 C 组合加载用户

E · 固定核心列 + JSON Metadata 列 Auth0 / PocketBase

  • 无需修改表结构，适合托管 SaaS
  • 每次请求 1 次 SQL
  • 扩展字段无静态类型检查
  • 无法对扩展字段建 SQL 外键约束
