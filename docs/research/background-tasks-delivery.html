为什么裸 enqueue 做不到真正的 At-Least-Once？

端到端投递保证由 4 个物理位置共同决定，缺一不可。

Stage 01 · 调用点 (Producer)
入队原子性
先 Commit 后 enqueue崩溃即丢任务
先 enqueue 后 CommitWorker 竞态 / 幽灵任务
enqueue_on(tx)与业务同事务提交
Stage 02 · 认领 (Claim)
Worker 崩溃回收
Early Ack取走即删 (AtMostOnce)
Lease / Reclaim超时回收 (AtLeastOnce)
Stage 03 · 异常 (Retry)
失败重试预算
max_attempts = 1报错直接 Failed
max_attempts > 1退避重回 Ready
Stage 04 · 函数体 (Handler)
业务副作用幂等
DB 写入唯一键 / 状态机
外部 API传 idempotency_key

主流库代码对照：Task 是什么类型？怎么 enqueue？

SQL 队列普遍用「默认参数 + 文档约定」；Actor 框架（Akka Typed）用「独立类型」在编译期强制区分。

Go · River 默认参数 MaxAttempts=25 + 文档推荐 InsertTx
  • Task 类型struct SyncBillArgs (实现 JobArgs)
  • 入队方法client.InsertTx(tx, args) / client.Insert(args)
  • 编译期限制无（任何 Job 都能裸调 Insert）
type SyncBillArgs struct { BillID int }
func (SyncBillArgs) Kind() string { return "sync_bill" }
func (SyncBillArgs) InsertOpts() river.InsertOpts {
    return river.InsertOpts{ MaxAttempts: 5 } // 不写默认 25
}

// 1. 事务入队（推荐）
_, err := client.InsertTx(ctx, tx, SyncBillArgs{BillID: 42}, nil)
// 2. 非事务入队（编译器不报错，存在丢任务窗口）
_, err  = client.Insert(ctx, SyncBillArgs{BillID: 42}, nil)
Rust · Underway 默认 RetryPolicy::default() + 双入队方法
  • Task 类型Job<Input, State>
  • 入队方法job.enqueue_using(&mut *tx, &in) / job.enqueue(&in)
  • 编译期限制泛型仅约束 Input，不约束是否进事务
let sync_bill: Job<SyncBill, ()> = Job::builder()
    .step(|_cx, SyncBill { id }| async move { To::done() })
    .name("sync_bill").pool(pool).build().await?;

// 1. 事务入队
sync_bill.enqueue_using(&mut *tx, &SyncBill { id: 42 }).await?;
// 2. 连接池直接入队（同样随时可调）
sync_bill.enqueue(&SyncBill { id: 42 }).await?;
Elixir · Oban 默认 max_attempts: 20 + Ecto.Multi
  • Task 类型Oban.Changeset (由 Worker.new/2 构造)
  • 入队方法Oban.insert(multi, name, cs) / Oban.insert(cs)
  • 编译期限制无（动态类型）
defmodule MyApp.SyncBill do
  use Oban.Worker, max_attempts: 5, unique: [period: 60]
  def perform(%Oban.Job{args: %{"id" => id}}), do: :ok
end

# 1. 绑进 Ecto.Multi 事务
Ecto.Multi.new()
|> Ecto.Multi.insert(:bill, bill_cs)
|> Oban.insert(:job, MyApp.SyncBill.new(%{id: 42}))
|> Repo.transaction()
Scala · Akka Typed 两套完全不同的类型（编译期强隔离）
  • AtMostOnce 类型ActorRef[Cmd] → 直接 ref ! msg
  • AtLeastOnce 类型ProducerController[Cmd] + Delivery[Cmd]
  • 编译期限制AtLeastOnce 严禁裸发，Consumer 强制带 confirmTo
// At-Most-Once：普通 ActorRef，直接 ! 发送
smsActor ! SendSms("13800000000")

// At-Least-Once：只能在收到 RequestNext 令牌时通过 sendNextTo 发送
case WrappedRequestNext(next) =>
  next.sendNextTo ! SyncBill(42)

// Consumer 端类型被强制包裹，必须显式发 Confirmed
case ConsumerController.Delivery(SyncBill(id), confirmTo) =>
  syncBill(id)
  confirmTo ! ConsumerController.Confirmed
Python · Django 6.0 (django.tasks) 仅定义接口契约，不含重试参数与 Worker
  • Task 类型django.tasks.Task
  • 入队方法task.enqueue(*args, **kwargs)
  • 事务结合靠 transaction.on_commit(...)（Commit 后崩溃仍会丢）
@task(priority=10, queue_name="default", takes_context=True)
def sync_bill(context: TaskContext, bill_id: int):
    # context.attempt 从 1 开始，但 @task 无 max_attempts 参数
    ...

with transaction.atomic():
    Bill.objects.create(id=42)
    # 注意：on_commit 在事务提交后执行，若此时进程崩溃，任务丢失
    transaction.on_commit(partial(sync_bill.enqueue, bill_id=42))
Python · Celery Per-Task 装饰器三元组切换语义
  • AtMostOnce (默认)acks_late=False, max_retries=0
  • AtLeastOnceacks_late=True, reject_on_worker_lost=True
  • 入队方法task.delay(...) / task.apply_async(...)
# 1. At-Most-Once（Worker 拿到消息先 ACK，崩溃绝不重跑）
@app.task(acks_late=False, max_retries=0)
def send_sms(phone: str): ...

# 2. At-Least-Once（执行完才 ACK，进程被杀自动重回队列）
@app.task(acks_late=True, reject_on_worker_lost=True, max_retries=5)
def sync_bill(bill_id: int): ...

框架 / 库 默认投递语义 靠什么约束用户？ 入队 API 能否混跑 AtMostOnce 与 AtLeastOnce？
Django 6.0 tasks 取决于第三方 Backend Feature Flags + 文档 task.enqueue() 无内置 per-task 区分
Celery At-Most-Once (Early Ack) @task(acks_late, max_retries) task.delay() 支持 (按 Task 装饰器配置)
Go River At-Least-Once (25 次重试) 默认参数 + 文档推荐 InsertTx InsertTx(tx) / Insert() 仅靠 MaxAttempts=1 近似
Rust Underway At-Least-Once 默认 RetryPolicy + 文档示例 enqueue_using(tx) / enqueue() 仅靠 RetryPolicy::never()
Elixir Oban At-Least-Once (20 次重试) 默认参数 + Ecto.Multi Oban.insert(multi, cs) 仅靠 max_attempts: 1
Scala Akka Typed At-Most-Once (Actor !) 编译期不同类型 ref ! msg vs sendNextTo ! msg 类型级严格区分
Dkron (运维 Cron) 基础设施定时触发 外部 Raft 集群 + HTTP Webhook 无代码级 enqueue 不适用（无法加入业务事务）
